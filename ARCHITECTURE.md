# Архитектура

Краткое описание того, как устроена система и как её части взаимодействуют.

## Общая схема

```
                    ┌──────────────────────────┐
   Браузер ───────▶  │  Frontend (HTML/CSS/JS)  │
                    └───────────┬──────────────┘
                                │  /api/... (same-origin)
                                ▼
                    ┌──────────────────────────┐        ┌──────────────┐
                    │        Backend           │◀──────▶│   ЮKassa     │
                    │  Fastify + SQLite (WAL)  │        └──────────────┘
                    └───────┬─────────┬────────┘
                            │         │
              ┌─────────────┘         └───────────────┐
              ▼                                       ▼
      ┌──────────────┐                        ┌──────────────┐
      │ SQLite DB    │                        │ SMTP (e-mail)│
      └──────────────┘                        └──────────────┘

   Админ-боты (Telegram / VK) ──HTTP──▶ Backend /api/...
```

Ключевой принцип: **единственный источник правды — backend**. Ни фронтенд,
ни боты не обращаются к базе данных напрямую — только через HTTP API.

## Backend

- **server.js** — точка входа: запуск Fastify (`buildApp()`), graceful shutdown.
- **src/app.js** — сборка приложения: CORS, helmet, rate-limit, content-type
  парсер, раздача статики
  `frontend/`, обработчик 404 для API и централизованный обработчик ошибок.
- **src/config/** — `env.js` (чтение и zod-валидация переменных окружения) и
  собранная конфигурация приложения.
- **src/db/** — соединение с SQLite (`better-sqlite3`, WAL-режим), миграции
  и репозитории (payments, sessions, schedule, reviews).
- **src/domain/** — доменная логика: `catalog` (услуги и цены), `slots`
  (формирование расписания).
- **config.json** — бизнес-данные: услуги, цены, параметры расписания.
- **src/controllers/** — HTTP-логика по доменам: payments, sessions, schedule,
  reviews, services, admin.
- **src/routes/** — монтирование роутов под `/api/...` и zod-схемы запросов.
- **src/services/** — интеграции: ЮKassa, e-mail, уведомления.
- **src/middleware/** — `auth` (API-ключи), `rateLimit` (лимитеры).
- **src/lib/** — `sessionBooking` (создание записи с защитой слота),
  `security` (аутентификация по ключам), `vkNotifier`, `text`.

### Модель данных (основное)

- `payments` — платёж ЮKassa: сумма, статус, контакты, `metadata` (в т.ч.
  черновик записи и токены доступа), `payment_id`.
- `sessions` — запись: клиент, услуга, дата/время, статус
  (`scheduled` / `completed` / `cancelled`), ссылка на платёж.
- `schedule_exceptions` — закрытые даты (выходные).
- `reviews` — отзывы с сайта.
- `payment_events` — добавочная история создания платежа и каждого фактического перехода
  статуса; текущее состояние остаётся в `payments` для быстрых запросов.

Денежные значения сохраняются в `amount_minor` как целое количество копеек. Поле `amount`
временно сохраняется как совместимое представление в рублях; миграция `005_integer_money`
заполняет копейки для уже существующих платежей и записей без изменения их значений.

Новые записи хранят фамилию, имя и необязательное отчество в отдельных колонках. Поля
`customer_name` и `client_name` остаются собранным отображаемым именем и обеспечивают
совместимость с существующими данными, ботами и старыми клиентами API. Старые ФИО не
разбираются автоматически, потому что надёжно определить части произвольной строки нельзя.

### Ключевые инварианты

- Запись создаётся **только после успешной оплаты**
  (вебхук, фоновая сверка или `POST /api/payments/:id/confirm-booking`).
- Подтверждение **идемпотентно**: повторный вызов возвращает уже созданную запись.
- Слот резервируется платежами в статусах `pending`/`succeeded`;
  повторное бронирование отдаёт `409 slot_taken`.
- Для групповых услуг одновременно проверяются вместимость и дубликат клиента.

## Frontend

- **js/config.js** — определение адреса API (same-origin / dev / override через
  `window.API_BASE_URL`) и ключ хранилища черновиков.
- **js/utils.js** — `apiRequest()` (единая обёртка над `fetch` с разбором ошибок),
  санитайзер, маска телефона.
- **js/booking.js** — пошаговая запись, валидация формы, календарь, создание
  платежа и сохранение черновика в `sessionStorage`.
- **js/payment-check.js** — опрос статуса платежа и вызов `confirm-booking`.
- **js/payment-failed.js** — показ причины и повтор оплаты из черновика.
- **js/gallery.js**, **js/reviews.js**, **js/ui.js**, **js/main.js** — галерея
  дипломов, отзывы, интерфейс и точка входа.

## Боты

- **bots-common/** — общее ядро: HTTP-клиент backend, форматирование записей,
  парсеры команд, напоминания/сводки, event-watcher.
- **telegram-bot/bot.py** — админ-панель Telegram (aiogram 3): расписание,
  статусы, статистика, экспорт `.ics`, напоминания.
- **vk-bot/bot.py** — админ-панель VK (vkbottle 4) с теми же возможностями и
  опциональным watcher для уведомлений о новых записях.

Оба бота работают через API и авторизуются ключом `BOT_API_KEY`
(должен совпадать с `BOT_API_KEYS` или `API_KEY` в окружении backend).

## Безопасность

- Секреты — только в `.env` (в репозиторий не попадают).
- Защищённые эндпоинты требуют API-ключ; публичные — лимитированы.
- Одноразовые токены платежа (`token`) ограничивают доступ к деталям платежа.
- HTML в уведомлениях экранируется; ввод санитизируется перед сохранением.
- Вебхук ЮKassa инициирует сверку статуса через API провайдера; ID, сумма и валюта проверяются по сохранённому платежу.
