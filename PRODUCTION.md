# Подготовка к запуску

Подготовлены код, тесты и отдельная конфигурация для одного постоянного сервера.
Это не отметка о выполненном production-развёртывании. Сервер и домен ещё не выбраны;
Docker-сборка, выпуск TLS-сертификата и реальная интеграция с ЮKassa требуют проверки
в целевой среде. SQLite нельзя размещать во временной файловой системе serverless.

## Проверки перед выкладкой

```sh
cd backend
npm ci
npm run check
npm run security:check
cd ..
python -B bots-common/test_access.py
```

В CI дополнительно проверяются зависимости, собираются backend, gateway и оба бота,
а также проверяются конфигурации Caddy и Compose. Production-образ зафиксирован на
Node.js 24.22.1 с обновлением безопасности от 21 октября 2026 года; ветка 24 является LTS:
https://nodejs.org/en/about/previous-releases

## Окружение

Создайте `.env.production` из `.env.production.example` на сервере. Задайте домен,
HTTPS `SITE_URL`, ключи ЮKassa, отдельные случайные `ADMIN_API_KEYS` и `BOT_API_KEYS`
длиной не менее 32 символов. Генератор ключей приведён в примере. Не храните реальные
секреты в Git. Сначала используйте тестовый магазин ЮKassa с `MOCK_MODE=false`.

Часовой пояс расписания задаётся `TZ` (по умолчанию `Europe/Moscow`). Не меняйте его
после появления записей без отдельной миграции: время сеансов хранится локальным.
Производственный режим отвергает mock-оплату, HTTP-адрес сайта, короткие ключи и
serverless-хранилище. При прямом запуске API `TRUSTED_PROXIES` пуст: forwarded-заголовки
игнорируются. В production Compose доверяется только IP контейнера gateway.

## Запуск после выбора площадки

DNS A/AAAA должны указывать на сервер; TCP 80 и 443 должны быть доступны. Caddy
получает и обновляет сертификат, перенаправляет HTTP на HTTPS:
https://caddyserver.com/docs/automatic-https

```sh
docker compose -f compose.production.yml --env-file .env.production config --quiet
docker compose -f compose.production.yml --env-file .env.production up -d --build
docker compose -f compose.production.yml --env-file .env.production ps
```

Backend не публикует порт наружу и работает под пользователем `node`. Gateway имеет
фиксированный адрес в отдельной Docker-сети. При конфликте подсети задайте согласованные
`APP_SUBNET` и `GATEWAY_IP` в `.env.production`. Перед подключением CDN/дополнительного
прокси отдельно настройте доверенные адреса и проверьте IP-лимиты. Нельзя включать
доверие ко всем forwarded-заголовкам.

Новый Compose использует named volumes. **Существующий `backend/data/payments.db`
туда автоматически не переносится.** Перед переносом остановите запись в старую систему,
создайте проверенную копию и импортируйте её в новый volume, затем сравните число
платежей/записей. Никогда не запускайте пустую БД вместо существующей.

Боты добавлены как необязательные Compose-профили. Перед включением задайте отдельный
`BOT_API_KEYS`, ID администраторов и токен выбранной платформы. Запуск Telegram:

```sh
docker compose -f compose.production.yml --env-file .env.production --profile telegram up -d --build
```

Для VK используйте `--profile vk`; оба профиля можно указать одной командой. Бот завершает
запуск, если не задан его администратор или ключ backend. Backend также может отправлять
уведомления сам по настройкам Telegram/VK/SMTP.

## Резервное копирование и восстановление

Сервис `backups` делает согласованный снимок SQLite при старте и затем каждые 24 часа.
Ошибка записывается в журнал, повтор — через 5 минут. Каждый снимок проверяется через
`integrity_check` и `foreign_key_check`. Обычное копирование только `.db` небезопасно,
пока приложение работает в WAL-режиме.

Команды из `backend`:

```sh
node scripts/database.js backup data/payments.db /secure-backups/payments-2026-10-21.db
node scripts/database.js verify /secure-backups/payments-2026-10-21.db
node scripts/database.js restore /secure-backups/payments-2026-10-21.db data/restored.db
```

Восстановление разрешено только в новый путь и не перезаписывает рабочую БД. Для
переключения остановите backend и ботов, проверьте восстановленную базу, настройте
`SQLITE_PATH` на неё и только затем запускайте приложение. Сохраните старую базу
вместе с WAL/SHM до проверки результата. При откате версии кода учитывайте совместимость
миграций: не заменяйте файлы БД работающего процесса.

Копии старше `BACKUP_RETENTION_DAYS` (по умолчанию 30 дней) автоматически удаляются
после успешного снимка. Удаление затрагивает только файлы с именами, созданными сервисом
`backups`. Named volume на том же сервере не защищает от потери сервера: настройте
шифрованную выгрузку во внешнее
хранилище, ограничение доступа и регулярное пробное восстановление. Целевой интервал
копирования/допустимую потерю данных нужно согласовать до приёма реальных клиентов.

## Наблюдение и приёмка

- Внешняя проверка `GET /api/health` каждые 1–5 минут, уведомление при недоступности.
- `GET /api/admin/operations` с `X-API-Key`: `stalePending` и `unconfirmedPaid` должны
  проверяться мониторингом; `needsAttention=true` требует сверки, а не удаления платежей.
- HTTP-удаление платежей и очистка базы отключены в production даже для администратора.
  Исправления финансовых записей выполняйте через документированную операторскую процедуру
  с резервной копией и журналом изменений.
- Журналы `backup_failed`, отсутствие `backup_completed` за 25 часов, ошибки сверки
  платежей и свободное место диска должны вызывать оповещение ответственному.
- Журналы API и nginx исключают query-параметры. Access log Caddy не включён.
  Не добавляйте полные URL оплаты/Referer в внешние средства аналитики и мониторинга.
- Настройте webhook `/api/admin/webhook` на `payment.succeeded` и `payment.canceled`.
  Пройдите оплату с закрытием браузера, повторную доставку, отказ провайдера и отмену.
- Проверьте восстановление после перезапуска, конкурентную запись на последнее место,
  восстановление из копии и получение писем/сообщений реальными адресатами.

Оставшиеся продуктовые решения: политика возвратов и отмены после оплаты. Сейчас отмена
записи **не выполняет автоматический возврат денег**. Также уведомления не имеют
долговечной очереди повторной доставки: запись сохраняется при сбое канала, но доставку
сообщения нужно контролировать по журналам. Эти ограничения нужно принять или доработать
до публичного запуска; они не скрываются успешными unit/integration-тестами.
